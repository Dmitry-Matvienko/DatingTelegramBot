# Записи архитектурных решений (ADR)

Журнал принятых и отклонённых архитектурных решений проекта DatingBot. Ведется в формате append-only.

---

### ADR-001: Применение Clean Architecture и строгой изоляции доменного ядра
- **Дата**: 2026-08-01
- **Статус**: Принято
- **Контекст**: Необходима гибкая, поддерживаемая и тестируемая кодовая база бота для знакомств с возможностью независимого развития логики поиска, подбора и интерфейса.
- **Решение**: Проект разделен на 4 слоя: `Domain`, `Application`, `Infrastructure`, `Bot`. Ядро `Domain` содержит 0 внешних зависимостей. Все сущности изолированы от атрибутов БД и Telegram API.
- **Последствия**: Обеспечена 100% тестируемость бизнес-логики без необходимости поднимать БД или Telegram Client.

### ADR-002: Конфигурация EF Core 9 через Fluent API
- **Дата**: 2026-08-02
- **Статус**: Принято
- **Контекст**: Требовалось сохранить чистоту слоя `Domain` и при этом иметь полный контроль над схемой таблиц, индексами и каскадными связями в MS SQL Server.
- **Решение**: Все маппинги вынесены в отдельные классы `IEntityTypeConfiguration<T>` в слое `Infrastructure`. Для уникальности и поиска созданы фильтрованные и композитные индексы (`TelegramId`, `CityId`, `FromUserId_ToUserId`).
- **Последствия**: Полный контроль над DDL, отсутствие загрязнения доменных моделей атрибутами `[Table]`/`[Key]`.

### ADR-003: 4-уровневый каскадный алгоритм подбора кандидатов (Matchmaking Tier System)
- **Дата**: 2026-08-05
- **Статус**: Принято
- **Контекст**: Пользователям нужно предлагать анкеты в порядке максимальной психологической, смысловой и географической релевантности, предотвращая исчерпание пула кандидатов в небольших городах.
- **Решение**: Внедрен 4-уровневый приоритетный алгоритм:
  - **Tier 1 (AI Compatibility)**: Семантическое сходство описаний для ИИ с косинусным расстоянием > 0.55.
  - **Tier 2 (Common Interests)**: Общие интересы (ранжирование по количеству совпадений).
  - **Tier 3 (Same City)**: Кандидаты из того же города.
  - **Tier 4 (Nearby City)**: Кандидаты из соседних городов в радиусе до 500 км, отсортированные по возрастанию расстояния (формула гаверсинусов).
- **Последствия**: Высокая точность подбора и бесшовная выдача анкет из соседних городов при исчерпании локального пула.

### ADR-004: Локальная in-process векторизация текста с аппаратным SIMD-ускорением
- **Дата**: 2026-08-08
- **Статус**: Принято
- **Контекст**: Использование внешних LLM/Embedding API (OpenAI/Cohere) создает задержки сети, денежные затраты на каждый запрос и зависимость от внешнего провайдера при массовом поиске по анкетам.
- **Решение**: Разработан `LocalAiEmbeddingService` — локальный легковесный векторизатор на основе n-граммного хеширования, генерирующий 384-мерные float-векторы с расчетом косинусного сходства через SIMD-векторы (`System.Numerics.Vector<float>`).
- **Последствия**: Мгновенный расчет совместимости (микросекунды), нулевая стоимость вычислений, полная автономность без сетевых запросов.

### ADR-005: Встроенный сжатый Gzip-датасет на 100 000+ городов мира
- **Дата**: 2026-08-10
- **Статус**: Принято
- **Контекст**: Полноценный гео-поиск требует базы городов мира с точными географическими координатами (широта, долгота) и странами.
- **Решение**: База из 100 000+ городов упакована в сжатый ресурс `cities_database.json.gz` (размер ~2.5 МБ). При первом запуске `CityDatabaseSeeder` автоматически распаковывает и пакетами загружает города в MS SQL Server.
- **Последствия**: Компактный размер репозитория, автоматическая инициализация координат всех городов без сторонних Geo API.

### ADR-006: Standalone Мультиязычный сервис (6 языков)
- **Дата**: 2026-08-15
- **Статус**: Принято
- **Контекст**: DatingBot ориентирован на международную аудиторию. Поддерживаются Русский, Украинский, Английский, Хинди, Португальский и Индонезийский языки.
- **Решение**: Реализован `LocalizationService` со статическим типобезопасным словарем строк, поддержкой форматирования параметров, корректными падежными формами (`TargetGender`) и локализацией справочника интересов.
- **Последствия**: Исключены ошибки отсутствующих переводов, обеспечена 100% изоляция языковых групп в поиске кандидатов.

### ADR-007: Внедрение стандарта Standing Orders и Spec-Driven Development (SDD)
- **Дата**: 2026-08-22
- **Статус**: Принято
- **Контекст**: Для предотвращения деградации контекста ИИ-агентов, потери архитектурных решений и неконтролируемых правок требуется структурированная постоянная память проекта.
- **Решение**: Проект переведен на трехуровневую систему управления (Standing Orders):
  - Уровень 1: Корневой `GEMINI.md` — точка входа, протокол сессии, иерархия истины, карта проекта.
  - Уровень 2: `docs/control/agent_rules.md` — устав и правила поведения.
  - Уровень 3: `docs/architecture/` (`architecture.md`, `decisions.md`) — архитектурный авторитет и ADR.
  - Уровень 4: `docs/architecture/specs/` — модульные спецификации подсистем (SDD).
  - Летопись: `docs/progress.md` с инвариантом `state_version`.
- **Последствия**: Прозрачный контроль над эволюцией кодовой базы, сохранение контекста между сессиями любого ИИ-ассистента.

### ADR-008: Обработка жалоб модераторами с инлайн-кнопками и мультиязычными уведомлениями
- **Дата**: 2026-08-22
- **Статус**: Принято
- **Контекст**: Ранее администраторы получали только уведомление о поступившей жалобе без возможности интерактивной обработки в один клик. Требовалось реализовать кнопки модерации («Заблокировать пользователя», «Удалить анкету», «Проигнорировать») с мгновенным автоматическим уведомлением заявителя и нарушителя.
- **Решение**:
  - Создан сервис `IModerationService` / `ModerationService` в слое `Application`.
  - Внедрен обработчик `AdminModerationCallbackHandler` в слое `Bot` с проверкой прав доступа через `BotConfiguration:AdminIds`.
  - Реализованы сценарии:
    - **Бан**: `UserState.Banned`, деактивация анкеты, блокировка дальнейших действий, уведомление заявителя и нарушителя.
    - **Удаление анкеты**: сброс полей анкеты, `UserState.None` / `Registration_SelectingLanguage`, уведомление заявителя и предупреждение нарушителю.
    - **Игнорирование**: отклонение без применения санкций.
  - Все сообщения локализованы на 6 языков (RU, UK, EN, HI, PT, ID) через `LocalizationService`.
  - Сообщение администратора автоматически редактируется для фиксации принятого решения и предотвращения повторных кликов.
- **Последствия**: Оперативная модерация контента напрямую из Telegram без входа в БД, защита пользователей и прозрачная обратная связь для заявителей.

### ADR-009: Панель администратора для рекламы, аналитики медиакита и сквозного поиска
- **Дата**: 2026-08-22
- **Статус**: Принято
- **Контекст**:
  - Администраторы не должны иметь анкеты знакомств в выдаче, но должны иметь стандартный пользовательский UI (`[ 🔍 Искать анкеты ]` и `[ 👤 Мой профиль ]`).
  - Для продажи рекламы необходимы точные цифры аудитории (медиакит): динамика за 24ч/7д/30д, срезы по полу, возрасту, топ городов и странам, а также цели аудитории (в количественном и процентном соотношении) и расчет охвата по конкретным городам.
  - Рекламодателям необходим конструктор таргетированных рассылок (с фото, текстом и инлайн URL-кнопкой) с безопасной доставкой без блокировок по rate-limit Telegram.
  - Администраторам необходим сквозной непрерывный просмотр всех анкет базы выбранного пола (без ограничений категорий целей/скоринга) с показом скрытого AI-описания, прямой ссылки на аккаунт Telegram, приветствия, рейтинга и кнопками прямого бана/удаления профиля (с уведомлением нарушителя), а также очередь неразобранных жалоб.
- **Решение**:
  - В слое `Domain`: сущность `ProfileReport` дополнена полями `IsResolved` (`bool`) и `ResolvedAt` (`DateTime?`). Добавлены FSM-состояния `Admin_*`.
  - В слое `Application`: спроектирован контракт `IAdminService` / `AdminService` с агрегацией DTO `AdminStatsDto`, `AdminCityStatsDto`, `AdminBroadcastFilterDto`, `AdminBroadcastResultDto` и операциями прямого бана/удаления.
  - В слое `Infrastructure`: реализованы агрегационные LINQ-запросы `UserProfileRepository` и конфигурация `IAdminSettings` для `AdminIds`.
  - В слое `Bot`: реализованы `AdminKeyboards`, `AdminPromptService`, `AdminBroadcastService` (с пакетной отправкой и троттлингом), `AdminCallbackHandler`, `AdminMessageHandler` и обновлен `TelegramUpdateRouter`.
  - Добавлена мультиязычность для всех админ-экранов на 6 языках в `LocalizationService`.
- **Последствия**: Полная автономия администратора в Telegram: готовность к коммерческим рекламным интеграциям, таргетированным рассылкам, мониторингу базы и оперативной модерации нарушителей.

### ADR-010: Подсистема учета доходов, финансового баланса бота и истории транзакций
- **Дата**: 2026-08-23
- **Статус**: Принято
- **Контекст**:
  - Требовалось добавить в главную панель администратора раздел «💰 Доход», предоставляющий информацию о текущем балансе звёзд Telegram Stars, общей сумме доходов, динамике за 24ч / 7д / 30д и детальном отчете по последним 20 транзакциям.
- **Решение**:
  - Создана доменная сущность `PaymentTransaction` с перечислением `PaymentType` (`Unban`, `Subscription`, `Other`) и миграция `Add_PaymentTransactions_Table`.
  - Реализован репозиторий `IPaymentTransactionRepository` / `PaymentTransactionRepository` с агрегацией финансовой аналитики и выборкой последних транзакций.
  - Расширен `IAdminService` / `AdminService` методами `GetRevenueStatsAsync`, `GetRecentTransactionsAsync` и `RecordSuccessfulPaymentAsync`.
  - В `TelegramUpdateRouter` подключена автоматическая фиксация платежей при успешной оплате через `message.SuccessfulPayment`.
  - В `AdminKeyboards` и `AdminPromptService` созданы экраны и клавиатуры баланса и истории транзакций (с кликабельными профилями плательщиков, суммами ⭐ и ID платежей).
  - Вся текстовая информация и кнопки локализованы на 6 языков (RU, UK, EN, HI, PT, ID).
- **Последствия**: Прозрачный финансовый мониторинг коммерческих поступлений бота в реальном времени с поддержкой Telegram Stars и историей транзакций.

### ADR-011: Механизм заманчивых напоминаний для неактивных пользователей (Inactivity Reminders)
- **Дата**: 2026-08-23
- **Статус**: Принято
- **Контекст**:
  - Для повышения возвращаемости (retention) и активности пользователей требовалось реализовать периодические заманчивые уведомления пользователям, не заходившим в бот заданное количество дней.
  - Необходимо 10 разнообразных заманчивых шаблонов (например, «с тобой хотят познакомиться», «найди свою любовь», «найди друзей» и др.) со случайным выбором при отправке.
  - Периодичность дней неактивности и интервал проверки должны задаваться в файле конфигурации `appsettings.json`.
- **Решение**:
  - В слое `Domain`: сущность `User` дополнена полями `LastActiveAt` (дефолт `DateTime.UtcNow`) и `LastInactivityReminderSentAt` (nullable).
  - В слое `Infrastructure`: обновлена конфигурация `UserConfiguration` с композитным индексом `IX_Users_LastActive_LastReminder` и создана миграция `Add_User_Inactivity_Tracking`. Добавлены методы репозитория `GetInactiveUsersAsync`, `MarkInactivityReminderSentAsync`, `UpdateLastActiveAtAsync`.
  - В слое `Application`: спроектирован сервис `IInactivityReminderService` / `InactivityReminderService` с генерацией случайного ключа шаблона (1..10) и выборкой неактивных пользователей. В `LocalizationService` добавлены 10 шаблонов и инлайн-кнопка перехода к поиску на 6 языках (RU, UK, EN, HI, PT, ID).
  - В слое `Bot`: создан фоновый сервис `InactivityNotificationWorker` (`BackgroundService`), запускающийся с настраиваемым интервалом `BotConfiguration:InactivityCheckIntervalMinutes` (дефолт 60 мин) и порогом неактивности `BotConfiguration:InactivityReminderDays` (дефолт 3 дня). В `TelegramUpdateRouter` подключена автоматическая фиксация активности при каждом входящем событии и обработка callback-кнопки `inactivity_search`.
- **Последствия**: Автоматизированное удержание и возвращение пользователей в воронку знакомств без спама и с соблюдением Clean Architecture и мультиязычности.

### ADR-012: Отказоустойчивая система инициализации и автоматического самовосстановления (Self-Healing Architecture)
- **Дата**: 2026-08-24
- **Статус**: Принято
- **Контекст**:
  - При холодном старте в облачных средах (Render, Docker) или сетевых задержках удаленная СУБД (SmarterASP.NET / Azure SQL) может быть кратковременно недоступна. Ранее блокирующий вызов миграций в `Program.cs` приводил к моментальному падению процесса (Crash-Loop) и блокировке Kestrel.
  - При временных перебоях связи с Telegram API, сетевых дропах, таймаутах или необработанных ошибках обработки апдейтов отдельного пользователя опрос Telegram Long Polling мог остановиться без автоматического восстановления.
- **Решение**:
  - Создан координатор состояния `IBotLifecycleCoordinator` / `BotLifecycleCoordinator` (`Singleton`), отслеживающий готовность БД (`IsDatabaseReady`), активность опроса Telegram (`IsTelegramPollingActive`), счетчики повторов и перезапусков, и предоставляющий асинхронную точку ожидания `WaitForDatabaseReadyAsync`.
  - Создан фоновый сервис неблокирующей инициализации `DatabaseBootstrapWorker` (`BackgroundService`), выполняющий миграции и сидирование с экспоненциальным backoff (3s -> 5s -> 10s -> 30s) без блокировки Kestrel Web-сервера и Keep-Alive пингов.
  - В `TelegramBotWorker` внедрен супервизорный цикл самовосстановления `while (!stoppingToken.IsCancellationRequested)` с экспоненциальным backoff при сбоях API / сети, изолированной обработкой входящих обновлений `ProcessUpdateSafeAsync` (гарантирующей, что сбой одного сообщения никогда не прервет опрос для остальных), и фиксацией ошибок в телеметрии.
  - В `Program.cs` настроен `HostOptions.BackgroundServiceExceptionBehavior = BackgroundServiceExceptionBehavior.Ignore` и глобальные перехватчики `AppDomain.CurrentDomain.UnhandledException` / `TaskScheduler.UnobservedTaskException`.
  - Эндпоинты `/` и `/health` дополнены подробной телеметрией готовности и самовосстановления.
- **Последствия**: 100% отказоустойчивость: бот самостоятельно восстанавливается после любых сбоев сети, СУБД или Telegram API, не прекращая отвечать на внешние пинги и не требуя ручного перезапуска.
