# Регламент работы с Git (Git Workflow & Branching)

## 1. Назначение

Настоящий документ регламентирует правила 3-уровневого ветвления, стандарты сообщений коммитов (Conventional Commits), разграничение ролей (Human Gatekeeper vs Autonomous Agent) и протокол работы с системой контроля версий Git в проекте **DatingBot**.

---

## 2. Стратегия 3-уровневого ветвления (3-Tier Branching Strategy)

```
main (Релиз / Production — под личным контролем ПОЛЬЗОВАТЕЛЯ)
 ▲
 │ (Инспекция и Merge: ТОЛЬКО Пользователь через PR или локальный merge)
 │
gemini (Финальная стабильная ветка ИИ-агента — 100% тестов, готово к ревью)
 ▲
 ├───► feature/user-filters (Разработка новой фичи) ───────┐
 │                                                         │ (Merge агентом после тестов)
 ├───► fix/rating-rounding (Исправление бага) ─────────────┼───► gemini
 │                                                         │
 └───► docs/standing-orders-update (Документация) ─────────┘
```

### 2.1. Иерархия и права доступа веток:

1. **`main`** — **Релизная ветка (Human Gatekeeper)**:
   - Содержит только утвержденный, проверенный пользователем код.
   - **Железный запрет для ИИ-агента:** Агенту **строго запрещено** делать прямые коммиты (`git commit`), слияния (`git merge`) или отправку (`git push`) в ветку `main`.
   - Ветка `main` обновляется **исключительно пользователем** после личной проверки ветки `gemini`.

2. **`gemini`** — **Финальная стабильная интеграционная ветка агента**:
   - Является единым источником правды для готовой работы агента.
   - В эту ветку агент собирает проверенные задачи из веток `feature/*`, `fix/*`, `docs/*`.
   - Перед каждым коммитом в `gemini` агент обязан прогнать **100% тестов** (`dotnet test DatingBot.sln`), подтвердить `0 failures` и обновить `docs/progress.md` (инкремент `state_version`).
   - Из ветки `gemini` агент выполняет `git push origin gemini` и запрашивает инспекцию у пользователя.

3. **Рабочие ветки задач (`feature/*`, `fix/*`, `docs/*`, `refactor/*`)**:
   - Создаются агентом от ветки `gemini` (или в изолированных worktrees) для конкретных задач:
     - `feature/<название>`: новые функции и сценарии.
     - `fix/<название>` / `hotfix/<название>`: исправление ошибок.
     - `docs/<название>`: спецификации, ADR, регламенты.
     - `refactor/<название>`: улучшение структуры кода.

## 3. Стандарт сообщений коммитов (Conventional Commits)

Формат каждого коммита:
```
<тип>(<область>): <краткое описание в повелительном наклонении>

[опциональное тело с подробностями]
```

### 3.1. Разрешенные типы:
- **`feat:`** Новая функциональность (например, `feat(search): add age range filter`).
- **`fix:`** Исправление ошибки в коде или локализации (например, `fix(loc): add missing accusative keys`).
- **`docs:`** Изменения в документации или спецификациях (например, `docs(spec): add admin_and_moderation spec`).
- **`test:`** Добавление или корректировка тестов (например, `test(matchmaking): add tests for nearby cities`).
- **`refactor:`** Правки кода без изменения внешнего поведения.
- **`chore:`** Служебные изменения (пакеты NuGet, `.gitignore`, конфигурация).

## 4. Протокол работы агента (Agent Git Lifecycle)

### 4.1. Старт работы над задачей:
1. Убедиться, что ветка `gemini` чистая и актуальная:
   ```bash
   git checkout gemini
   git status
   ```
2. Создать ветку под задачу:
   ```bash
   git checkout -b feature/my-feature
   ```
   *(или использовать изолированный worktree через `using-git-worktrees`)*.
3. Прогнать baseline-тесты: `dotnet test DatingBot.sln`.

### 4.2. В процессе разработки:
- Следовать циклу **TDD** (`test-driven-development`): сначала падающий тест, затем минимальный код.
- При возникновении багов следовать **Systematic Debugging**.
- Делать логические коммиты в ветку задачи: `git commit -m "..."`.

### 4.3. Интеграция в стабильную ветку `gemini`:
1. Прогнать полный пакет тестов: `dotnet test DatingBot.sln` (**100% green**).
2. Запросить код-ревью через `code-reviewer-agent` (`requesting-code-review`).
3. Обновить `docs/progress.md` (отметить выполненные задачи, **увеличить `state_version` на 1**).
4. Переключиться на `gemini`, слить ветку задачи и удалить временную ветку:
   ```bash
   git checkout gemini
   git merge feature/my-feature
   dotnet test DatingBot.sln
   git branch -d feature/my-feature
   ```
5. Отправить стабильную ветку `gemini` в удаленный репозиторий:
   ```bash
   git push origin gemini
   ```
6. **Доложить пользователю о готовности к инспекции.**

## 5. Протокол инспекции и слияния пользователем (Human Gatekeeper)

Пользователь проверяет изменения и производит слияние в `main` одним из двух способов:

* **Способ А (Через GitHub / GitLab Pull Request — Рекомендуется):**
  1. Пользователь открывает PR: `gemini -> main`.
  2. Проверяет Diff файлов и CI-статус.
  3. Нажимает **Merge Pull Request**.

* **Способ Б (Локально в консоли):**
  ```bash
  git checkout main
  git merge gemini
  dotnet test DatingBot.sln
  git push origin main
  ```

### 5.1. Синхронизация агента после слияния в `main`:
После того как пользователь обновил `main`, агент синхронизирует ветку `gemini`:
```bash
git checkout gemini
git merge main
```

---

## 6. Протокол безопасного отката (Rollback Policy)

- **Откатить незакоммиченные изменения:** `git restore .`
- **Удалить неудачную ветку задачи:** `git checkout gemini && git branch -D feature/broken-experiment`
